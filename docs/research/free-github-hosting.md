# Free auto-deploy hosting for this app: primary-source research

Scope: for a non-developer choosing among free, auto-build-on-`git push` static hosts for this Vite + React web app — GitHub Pages, Netlify, Vercel, Cloudflare Pages, and brief mentions of Surge.sh and Render — what each host requires, what its free tier actually allows, and specifically whether it can replace the dev-only `/api/metro` reverse proxy (a server that quietly forwards a request to another server, here so it can add a header the browser is not allowed to add) that today only exists in `vite.config.js`'s local dev server.

Jargon used below, defined once: **build minutes** (CPU time a host's server spends running your `npm run build`, metered separately from the traffic your site serves), **bandwidth** (data transferred to visitors, usually billed by the GB), **serverless/edge function** (a small piece of server-side code the host runs on demand per request, instead of you running your own server continuously — "edge" means it runs at a data-centre near the visitor rather than one central region), **reverse proxy** (a server that sits between the visitor and a third-party API, forwarding the request — used here so it, not the browser, can add the header the third-party API demands), **cold start** (the delay the first request to an idle serverless function pays while the host spins up a fresh instance), **CDN** (Content Delivery Network — a network of edge servers that caches and serves your static files from a location near each visitor), **CNAME** (a DNS record type used to point a custom domain at a host's servers).

## 1. The finding that should decide this: the `/api/metro` proxy is real, confirmed in this repo, and only two of the four hosts fix it without extra code

`vite.config.js` runs a dev-only server proxy: `server.proxy['/api/metro']` forwards to `https://metroapi.alexbadi.es` and injects `User-Agent: vib-metro-valencia/1.0 (Web; contact=dev@example.com)` on the outbound request (`vite.config.js` lines 42–51). `src/services/arrivalStore.js` (lines 356–377) explains why: `metroapi.alexbadi.es` requires a `User-Agent` containing `contact=`, and browser `fetch()` can never set `User-Agent` — it is a forbidden header, unconditionally, in every browser, per the Fetch spec. In the browser build the app calls the relative path `/api/metro/prevision/{stationId}/parse` with no `User-Agent` at all and relies on the dev proxy to add it server-side; the native iOS build instead calls `https://metroapi.alexbadi.es` directly through `CapacitorHttp`, which is not a browser fetch and is not subject to that restriction, so it can set the header itself.

**A plain static build has no dev server, so `/api/metro/...` resolves to nothing on any of these hosts by default — the arrivals feature silently breaks unless the host is given something to replace the proxy.** What each host can actually do about it, confirmed against its own docs:

1. **Netlify — solved with a config file, no code required.** Netlify's redirects/rewrites let a rule proxy a path to an external URL *and* attach custom request headers to that outbound request: "For redirect rules specified in the Netlify configuration file, you can add a map with custom headers for your proxy redirects, and Netlify will send the custom headers to another website with every request" ([Netlify Docs, Rewrites and proxies](https://docs.netlify.com/manage/routing/redirects/rewrites-proxies/)). This is a server-side proxy Netlify itself operates when it relays the request — not the visitor's browser — so the forbidden-header restriction never applies; a `netlify.toml` entry with `headers = {User-Agent = "..."}` on a `/api/metro/*` → `https://metroapi.alexbadi.es/:splat` redirect is a near-exact drop-in replacement for the current dev proxy. Note the one caveat the docs give: this only works in `netlify.toml`, not in a plain `_redirects` file, and custom headers apply to the *outbound* request, not to whatever comes back to the visitor.

2. **Vercel — needs a small serverless function, and the "no-code" Edge option is a trap.** `vercel.json` `rewrites` can forward `/api/metro/*` to `https://metroapi.alexbadi.es/*` as a reverse proxy ([Vercel Docs, Rewrites](https://vercel.com/docs/routing/rewrites)), but nothing in that rewrite configuration lets you attach a custom request header to the proxied call — the only header options documented are response-caching headers (`CDN-Cache-Control` etc.), not headers sent to the upstream origin. So a rewrite alone cannot inject `User-Agent`. The fix is a one-file serverless function (e.g. `api/metro.js`) that does the `fetch(...)` itself with the header set in code — but it must run on Vercel's **Node.js runtime**, not the Edge runtime: Vercel's Edge Functions forcibly overwrite any custom `User-Agent` you pass to `fetch()`, replacing it with a fixed string like `"Vercel Edge Functions"`, a limitation confirmed as Edge-runtime-specific in [a Vercel/Next.js GitHub issue](https://github.com/vercel/next.js/issues/31085) and not present in the [Node.js runtime](https://vercel.com/docs/functions/runtimes/node-js), which supports the ordinary Node fetch/Web APIs with no such override.

3. **Cloudflare Pages — `_redirects` explicitly cannot do this; a Pages Function is required.** Cloudflare's own docs state the limitation plainly: "Proxying will only support relative URLs on your site. You cannot proxy external domains" ([Cloudflare Pages, Redirects](https://developers.cloudflare.com/pages/configuration/redirects/)) — so the config-file route that works for Netlify is a dead end here. The real fix is a Pages Function (Cloudflare's serverless model, built on Workers) at `functions/api/metro/[[path]].js` that does the `fetch()` server-side. This is not a code-free path, but it is friendlier than Vercel's Edge trap: "compared to browsers, Cloudflare Workers impose very few restrictions on what headers you are allowed to send" and `User-Agent` is not one of the blocked ones, so a Worker/Pages Function can set it directly with no runtime-specific gotcha.

4. **GitHub Pages — not possible at all on the platform itself.** GitHub Pages serves only pre-built static files; it has no server-side rewrite/proxy layer and no serverless-function product of its own ([GitHub Docs, About GitHub Pages](https://docs.github.com/en/pages/getting-started-with-github-pages/about-github-pages) describes it purely as static-site hosting built from a repository, with no mention of any request-time compute). There is no config file or dashboard toggle that fixes this on GitHub Pages. The only way to keep arrivals working from a GitHub Pages–hosted front end is to run the proxy somewhere else entirely (e.g. a small Cloudflare Worker or Netlify Function deployed separately) and point the static site's `fetch()` at that external URL instead of a same-origin `/api/metro` path — which is extra infrastructure, not a one-file fix.

**Practical takeaway:** this single issue is a bigger differentiator between these hosts, for this app, than any bandwidth or build-minute limit below — it is the difference between "add one file to the repo and the feature works" (Netlify) and "the feature is quietly broken until you build and deploy a second thing" (GitHub Pages).

## 2. GitHub Pages + GitHub Actions

**Trigger and setup.** A GitHub Actions workflow deploying to Pages is triggered "whenever there is a push to the default branch of the repository or whenever the workflow is run manually from the Actions tab" ([GitHub Docs, Configuring a publishing source](https://docs.github.com/en/pages/getting-started-with-github-pages/configuring-a-publishing-source-for-your-github-pages-site)). The standard workflow checks out the repo, runs the build, uploads the `dist` folder with `actions/upload-pages-artifact`, and publishes it with `actions/deploy-pages`; GitHub creates the required `github-pages` deployment environment automatically the first time it runs. This is not zero-config: a workflow YAML file in `.github/workflows/` is required (this repo currently has none), and — Vite-specific — the [Vite static deploy guide](https://vite.dev/guide/static-deploy.html) is explicit that "GitHub will now deploy your site using a GitHub Actions workflow, which is necessary since Vite requires a build step for deployment," and gives a ready-made sample workflow.

**The base-path gotcha.** This is the well-known trap for a Vite project site: a repo served at `username.github.io/repo-name/` (as opposed to a custom domain, or a repo literally named `username.github.io`) needs `base: '/repo-name/'` set in `vite.config.js`, or every asset URL the built `index.html` references resolves one level too high and the page loads blank. A custom domain or a `username.github.io` root site instead needs `base: '/'` (the Vite default) ([Vite, Deploying a Static Site](https://vite.dev/guide/static-deploy.html)). Every one of the other three hosts below serves each project from its own domain root, so this specific gotcha does not exist on Netlify, Vercel, or Cloudflare Pages.

**Free tier limits (all stated as "soft" — advisory, not hard-enforced cutoffs).** A GitHub Pages site has a soft bandwidth limit of 100 GB per month, a soft limit of 10 builds per hour (waived entirely if you build with a custom GitHub Actions workflow, which this app would need anyway), and published sites may be no larger than 1 GB ([GitHub Docs, GitHub Pages limits](https://docs.github.com/en/pages/getting-started-with-github-pages/github-pages-limits)).

**Commercial-use restriction.** GitHub Pages "is not intended for or allowed to be used as a free web-hosting service to run your online business, e-commerce site, or any other website that is primarily directed at either facilitating commercial transactions or providing commercial software as a service (SaaS)" (same source) — a hobby transit map is squarely inside the allowed use.

**HTTPS / custom domain.** Free and automatic: when a custom domain is set, GitHub automatically requests and installs a Let's Encrypt certificate, and an "Enforce HTTPS" toggle transparently redirects HTTP to HTTPS once available (it can take up to 24 hours to appear) ([GitHub Docs, Securing your GitHub Pages site with HTTPS](https://docs.github.com/en/pages/getting-started-with-github-pages/securing-your-github-pages-site-with-https)).

**The `/api/metro` problem:** unsolved on-platform — see §1.4.

## 3. Netlify

**Trigger and setup.** Connecting a Git repository (GitHub, GitLab, Bitbucket, or Azure DevOps) means "every push to your connected branch automatically triggers a new deployment," and Netlify additionally builds a Deploy Preview for every pull request and commit so you can check a change before merging it into production ([Netlify Docs, Get started](https://docs.netlify.com/get-started/)). No config file is required for a plain Vite app: "Netlify auto-detects your framework for you and sets default build settings for you unless you or your code specified other build settings" — the build command and the `dist` publish directory are both detected automatically. A `netlify.toml` only becomes necessary here for the `/api/metro` redirect rule described in §1.1.

**Free tier limits.** Netlify moved new signups to a credit-based free plan (accounts created before 4 September 2025 keep the older 100 GB bandwidth / 300 build-minute model). On the current Free plan: **$0/month, 300 credits/month, hard limit with no overage** ([Netlify Docs, Credit-based pricing plans](https://docs.netlify.com/manage/accounts-and-billing/billing/billing-for-credit-based-plans/credit-based-pricing-plans/)); bandwidth costs 20 credits per GB served, so 300 credits alone covers roughly 15 GB of traffic a month before anything else (builds, functions) is spent from the same pool — a real ceiling for a public map that could see bursts of traffic, unlike GitHub Pages' 100 GB soft limit. The Free plan also caps you at 500 projects, 1 concurrent build at a time, and 1 Team Owner (same source). Custom domains with free SSL and serverless functions are both included on the Free plan.

**The `/api/metro` problem:** solved with a config-file redirect, no serverless function needed — see §1.1. This is the strongest practical argument for Netlify for this specific app.

## 4. Vercel

**Trigger and setup.** Vercel "automatically deploys supported Git repositories on every branch push and when changes merge into the production branch" ([Vercel Docs, Deploying Git Repositories](https://vercel.com/docs/git)): every push to a non-production branch gets its own Preview Deployment URL, and a push/merge to the production branch (`main` by default) triggers a Production Deployment. Vite is auto-detected via a Framework Preset when importing the repo — no `vercel.json` is required for a plain build; one becomes necessary only for the `/api/metro` rewrite and its accompanying serverless function.

**Free tier limits (Hobby plan).** The Hobby plan is explicitly described as "aimed at developers with personal projects, and small-scale applications" and — importantly — its fair-use terms restrict it to **"non-commercial, personal use only"** ([Vercel Docs, Hobby Plan](https://vercel.com/docs/plans/hobby); [Fair use guidelines](https://vercel.com/docs/limits/fair-use-guidelines#commercial-usage)), which is a real check for anyone weighing donations/ads later but is fine for a personal transit map today. Included usage: up to 1,000,000 Edge Requests, up to 200 projects, up to 100 deployments per day, up to 50 custom domains per project, 4 CPU-hours and 360 GB-hours of function compute, and the first 1,000,000 function invocations, with functions capped at a 300-second max duration on Hobby (same source). Exceeding most limits pauses the affected feature for roughly 30 days rather than billing you.

**The `/api/metro` problem:** solvable, but only with a serverless function on the **Node.js** runtime, not Edge — see §1.2 for the specific Edge-runtime `User-Agent` override that makes the "quick" Edge Function path a trap here.

## 5. Cloudflare Pages

**Trigger and setup.** Git integration gives "automatic builds and deployments every time you push a change to your connected GitHub or GitLab repository" ([Cloudflare Docs, Git integration](https://developers.cloudflare.com/pages/get-started/git-integration/)): the configured production branch (typically `main`) triggers production deploys, every other branch gets its own preview deployment, and pull requests are updated with preview links automatically. Unlike Netlify/Vercel, Cloudflare's docs do not claim automatic Vite framework detection with zero input — the dashboard offers a Vite-flavoured "framework preset" that pre-fills the build command and output directory, but you still confirm (or type) `npm run build` and `dist` once during project setup; no ongoing config file is required after that for the build itself.

**Free tier limits.** Static-asset requests and bandwidth are unmetered on every plan, including free: "requests to static assets are free and unlimited... All plans come with unlimited sites, seats, requests, and bandwidth" for that static-asset traffic. The catch is Pages Functions (the serverless layer, needed here for the `/api/metro` proxy): Functions requests draw from the same 100,000-requests-per-day free quota shared with Cloudflare Workers ([Cloudflare Docs, Pages Functions pricing](https://developers.cloudflare.com/pages/functions/pricing/)) — plenty for a low-traffic personal map's arrivals polling, but worth knowing it is not unlimited the way the static map tiles/JS/CSS are. Build limits: 1 build running at a time, up to 500 builds per month, a 20-minute build timeout, up to 100 projects per account, up to 20,000 files per site, 25 MiB per file, and up to 100 custom domains per project ([Cloudflare Docs, Limits](https://developers.cloudflare.com/pages/platform/limits/)).

**The `/api/metro` problem:** solvable, but requires writing a Pages Function (not just a config file) — see §1.3. Once written, Cloudflare's own docs note Workers/Pages Functions face "very few restrictions" on outbound headers compared to a browser, so `User-Agent` sets cleanly with no Vercel-style runtime trap.

## 6. Brief secondary mentions: Surge.sh and Render

**Surge.sh** is CLI-first, not Git-integrated the way the others are: its own docs describe publishing "straight from the command line," and automating it means minting a token (`surge tokens add`) and running the `surge` CLI yourself inside a CI pipeline such as a GitHub Actions workflow ([Surge, Getting Started](https://surge.sh/docs/getting-started)) — so it does not give a push-and-it-just-works flow out of the box the way GitHub Pages Actions, Netlify, Vercel, and Cloudflare Pages all do; you'd be hand-building the GitHub Actions equivalent anyway, at which point GitHub Pages itself is the simpler choice. Its docs do confirm free custom domains with automatically-provisioned, auto-renewing SSL. It has no serverless/edge function product, so it could not host the `/api/metro` proxy at all.

**Render** is a general app-hosting platform (static sites, web services, cron jobs, databases) rather than a Jamstack-specialist static host; it is capable of running the actual proxy as a small persistent Node web service with git-push auto-deploys, which would sidestep the serverless-cold-start question entirely, but that is a heavier setup (a second service to configure and keep from spinning down) than this project needs given Netlify already solves the proxy with a two-line config entry. Not investigated in the same depth as the four required hosts above, since it doesn't change the recommendation.

## 7. Other gotchas relevant to this specific hobby project

- **`data/valencia_rails.json` and similar large data files (~1.5 MB) are not a problem for any of these hosts.** Cloudflare Pages' 25 MiB per-file cap and 1 GB (GitHub Pages) / no stated static-file cap (Netlify, Vercel) are all far above 1.5 MB; none of these hosts requires Git LFS for a file this size. Git LFS only becomes relevant if a single asset ever approaches these per-file ceilings.
- **No GitHub organization is required for any host.** All four integrate with a personal GitHub account; GitHub Pages, Netlify, and Vercel Hobby all explicitly support personal-account repos, and Cloudflare Pages' Git integration works the same way for personal accounts.
- **Cold starts / sleep behavior**: GitHub Pages and Cloudflare Pages' static layer never sleep — they are plain CDN-served files. Netlify's and Vercel's serverless functions (only relevant if the `/api/metro` proxy is implemented as a function rather than a config-level redirect) can incur a brief cold-start delay on the first request after idling, which would show up as the very first arrivals fetch after a period of no visitors being slightly slower — inconsequential for a low-traffic personal project, but worth knowing it's there. Netlify's config-file redirect approach for this app sidesteps that entirely since no function is invoked.
- **Monorepo/subdirectory quirks**: not applicable — this repo is a single Vite app at its root, so none of the four hosts needs a "root directory" override during setup (Vercel and Cloudflare Pages both expose one in their dashboards for monorepos, unused here).
- **This repo's `postbuild` script (`npx cap sync ios`) is iOS-only bookkeeping.** All four hosts run `npm run build`, which triggers this postbuild step; on a Linux build machine with no iOS/Xcode toolchain, Capacitor's `cap sync ios` is expected to no-op or fail safely rather than break the whole build, but this is worth a one-time smoke test on whichever host is chosen, since a postbuild script that unexpectedly exits non-zero would fail the entire deploy.

## Recommendation

**Netlify is the clear best fit for this project.** It matches GitHub Pages, Vercel, and Cloudflare Pages on the basics that matter to a non-developer — push to `main` and the site rebuilds and goes live automatically, Vite's build command and `dist` output are auto-detected with no config file needed for the build itself, custom domains get free automatic HTTPS, and its free-tier commercial-use posture (personal projects are fine) matches this hobby project. What sets it apart is the one problem specific to this codebase: the `/api/metro` reverse proxy that today only exists inside `vite.config.js`'s dev server. Netlify is the only one of the four required hosts where that proxy can be reproduced with a config file alone — a `netlify.toml` redirect rule that forwards `/api/metro/*` to `https://metroapi.alexbadi.es/*` and attaches the same `User-Agent: ... contact=...` header the dev proxy sets today, with no serverless function to write, deploy, or maintain, and no runtime-specific trap to trip over (Vercel's Edge Functions silently strip a custom `User-Agent`; Cloudflare's `_redirects` cannot proxy off-site at all, so it needs an actual Pages Function; GitHub Pages cannot do this at all). For a non-expert maintaining a personal project, "add one file to the repo" beats "write and deploy a small server-side function" on every host it's being compared against, and beats "the arrivals feature just doesn't work" on GitHub Pages.
